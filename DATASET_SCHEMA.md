# LoquaciousSet Medium — Mimi Semantic Cache

## Назначение

Кеш предназначен для обучения и оценки моделей Manifestro, использующих
дискретный семантический поток Mimi. Он содержит:

1. метаданные исходного аудио из `speechbrain/LoquaciousSet`
   (`medium`, официальный `dev` и официальный `test`);
2. нормализованный текст транскрипции;
3. семантические коды Mimi для каждого аудио.

Кеш **не содержит** `byte_targets`, акустические кодбуки Mimi, mel-спектрограммы,
эмбеддинги или скрытые состояния. `byte_targets` при необходимости вычисляются из
нормализованного текста в training pipeline.

## Формат набора данных

Основной формат — шардированные Parquet-файлы.

```text
loquacious-medium-mimi/
├── train/
│   ├── train-00000.parquet
│   └── ...
├── validation/
│   ├── validation-00000.parquet
│   └── ...
├── test/
│   ├── test-00000.parquet
│   └── ...
├── dataset_info.json
├── shards.jsonl
├── splits.jsonl
├── processing_stats.json
└── failures.jsonl
```

Рабочие имена шардов не содержат `of-N`: итоговое количество шардов заранее
неизвестно и может измениться после обработки ошибок. При необходимости после
завершения можно отдельно собрать Hugging Face release с финальными именами.

Разделение данных сохраняется строго:

- `medium/train` используется для обучения;
- официальный Loquacious `dev` используется как `validation`;
- официальный Loquacious `test` резервируется для финальной оценки.

`medium`, `dev` и `test` нельзя объединять или переразбивать до создания кеша.

## Схема записи

| Поле | Тип | Обязательное | Описание |
|---|---|---:|---|
| `sample_id` | `string` | да | Уникальный стабильный идентификатор записи в кеше. |
| `source_id` | `string` | да | Устойчивый идентификатор исходной записи в LoquaciousSet. |
| `source_config` | `string` | да | Исходная конфигурация LoquaciousSet: `medium`, `dev` или `test`. |
| `source_split` | `string` | да | Исходный split записи. |
| `source_shard` | `string` | да | Устойчивое имя исходного Parquet-шарда без локального cache path. |
| `source_row_index` | `int64` | да | Нулевая позиция записи внутри исходного шарда. |
| `speaker_id` | `string` | да | Идентификатор диктора из исходного датасета. Пустая строка, если неизвестен. |
| `chapter_id` | `string` | да | Идентификатор главы/сессии из источника. Пустая строка, если неприменим. |
| `source_audio_name` | `string` | да | Устойчивое имя аудио из источника; не локальный абсолютный путь. |
| `source_sample_rate` | `int32` | да | Частота дискретизации исходного аудио в Hz. |
| `source_num_samples` | `int64` | да | Количество сэмплов в исходном аудио до ресемплинга для Mimi. |
| `audio_seconds` | `float32` | да | Длительность исходного аудио в секундах. |
| `original_text` | `string` | да | Исходная транскрипция без нормализации. |
| `normalized_text` | `string` | да | Нормализованная транскрипция, используемая downstream pipeline. |
| `semantic_codes` | `list<uint16>` | да | Последовательность семантических токенов Mimi в хронологическом порядке. |
| `semantic_length` | `int32` | да | Число элементов в `semantic_codes`. |

Для успешной записи null-значения не допускаются. Отсутствующие необязательные
идентификаторы представлены пустой строкой, чтобы схема оставалась стабильной.

## Семантические коды Mimi

- Сохраняется только семантический поток Mimi.
- Индекс выбранного кодбука фиксируется в `dataset_info.json`.
- Коды сохраняются без дополнительной агрегации, сегментации или изменения порядка.
- Одна запись датасета соответствует одной последовательности `semantic_codes`.
- `semantic_length` всегда равен `len(semantic_codes)`.
- Временная позиция токена восстанавливается через Mimi frame rate, записанный в
  `dataset_info.json`; отдельные timestamps не сохраняются.

Конкретный checkpoint Mimi и индекс семантического кодбука должны быть утверждены
до полного прогона. Нельзя объединять в одном кеше токены от разных checkpoint или
разных реализаций Mimi.

## Нормализация текста

`normalized_text` должен создаваться одной детерминированной, версионированной
функцией. До полного прогона необходимо утвердить точные правила для:

- Unicode-нормализации;
- регистра;
- пробельных символов;
- пунктуации и апострофов;
- чисел, сокращений и специальных символов;
- пустых транскрипций.

Версия нормализатора и его конфигурация фиксируются в `dataset_info.json`.
`original_text` сохраняется рядом с `normalized_text`, чтобы normalizer можно было
изменить без повторного запуска Mimi над 2 500 часами аудио.

## `dataset_info.json`

Файл содержит общую provenance-информацию, которая не должна повторяться в каждой
строке Parquet:

```json
{
  "schema_version": "1.0.0",
  "dataset_id": "speechbrain/LoquaciousSet",
  "dataset_configs": ["medium", "dev", "test"],
  "dataset_revision": "<immutable revision>",
  "mimi_model_id": "<model id>",
  "mimi_model_revision": "<immutable revision>",
  "mimi_model_sha256": "<sha256>",
  "mimi_implementation": "<package and version>",
  "mimi_sample_rate": "<integer Hz>",
  "mimi_frame_rate": "<number frames/sec>",
  "semantic_codebook_index": "<integer>",
  "semantic_codebook_size": "<integer>",
  "semantic_code_dtype": "uint16",
  "target_audio_hours_per_shard": 25,
  "audio_channel_policy": "<mono conversion policy>",
  "resampler": "<implementation and configuration>",
  "text_normalizer_version": "<version>",
  "processing_code_revision": "<revision>",
  "created_at_utc": "<ISO-8601 timestamp>"
}
```

Placeholder-значения заменяются фактическими параметрами до публикации кеша.

## Размер и завершение шардов

Целевой размер рабочего Parquet-шарда — 25 часов аудио. Граница определяется по
сумме `audio_seconds`, а не по числу примеров. Последний шард каждого split может
быть меньше. Незначительное превышение 25 часов допустимо для сохранения записи
целиком.

`shards.jsonl` является append-only manifest для resume. Одна завершённая запись:

```json
{
  "split": "train",
  "shard_index": 17,
  "path": "train/train-00017.parquet",
  "status": "complete",
  "examples": 12104,
  "audio_seconds": 89961.4,
  "semantic_tokens": 1124517,
  "sha256": "<sha256>",
  "source_shards": ["<source shard>"],
  "last_source_shard": "<source shard>",
  "last_source_row_index": 12003,
  "completed_at_utc": "<ISO-8601 timestamp>"
}
```

`last_source_shard` и `last_source_row_index` образуют точный resume cursor в
детерминированном порядке исходных шардов. Одного списка `source_shards` для
возобновления недостаточно, потому что последний source shard может быть обработан
частично.

Шард считается завершённым только после следующей последовательности:

1. запись в временный файл в том же filesystem;
2. закрытие и повторное открытие файла;
3. проверка Arrow-схемы, количества строк и всех инвариантов;
4. вычисление SHA-256;
5. атомарное переименование в итоговый путь;
6. добавление в `shards.jsonl` строки со `status: complete`.

При resume обрабатываются только исходные записи, которые не покрыты завершёнными
шардами. Наличие одного лишь временного или итогового Parquet-файла без валидной
строки `status: complete` не считается подтверждением завершения.

После полного исчерпания источника split получает запись `status: complete` в
`splits.jsonl`. Она создаётся только после сохранения последнего успешного шарда и
фиксирует последний просмотренный source cursor, включая случай, когда в конце
источника были только ошибочные записи. Это предотвращает бесконечную повторную
обработку ошибочного хвоста при `--resume`.

## Обязательные инварианты

Для каждой успешной записи проверяется:

```text
sample_id уникален
source_sample_rate > 0
source_num_samples > 0
audio_seconds > 0
abs(source_num_samples / source_sample_rate - audio_seconds) <= tolerance
normalized_text не пустой
original_text не пустой
semantic_length == len(semantic_codes)
semantic_length > 0
0 <= semantic_codes[i] < semantic_codebook_size
semantic_length соответствует длительности с учётом Mimi frame rate и codec padding
```

Дополнительно пакетное кодирование должно быть проверено на эквивалентность
одиночному кодированию после удаления padding:

```text
encode(audio отдельно) == encode(audio в batch)
```

## Ошибки и статистика

Повреждённые или необрабатываемые записи не включаются в основные Parquet-шарды.
Они записываются в `failures.jsonl` с полями:

```text
sample_id, source_id, source_config, source_split, source_shard,
source_row_index, source_audio_name, error_type, error_message
```

`processing_stats.json` должен содержать как минимум:

- количество найденных, успешно обработанных и пропущенных записей;
- количество и длительность успешно обработанного аудио;
- количество и длительность пропущенного аудио;
- распределение ошибок;
- минимум, максимум и среднее для `audio_seconds` и `semantic_length`;
- фактическую скорость обработки и используемое устройство.

## CLI и наблюдаемость

Запуск должен выполняться через `uv` и предоставлять единый CLI:

```bash
# Короткий тест производительности и подбор безопасного batch budget.
uv run aether-dataset benchmark --config configs/loquacious-medium.yaml

# Новый прогон.
uv run aether-dataset run --config configs/loquacious-medium.yaml

# Продолжение прерванного прогона без перезаписи готовых шардов.
uv run aether-dataset run --config configs/loquacious-medium.yaml --resume

# Просмотр состояния по сохранённому manifest без запуска Mimi.
uv run aether-dataset status --output /data/loquacious-medium-mimi

# Полная проверка уже созданного кеша.
uv run aether-dataset validate --output /data/loquacious-medium-mimi

# Публикация выполняется только после полной валидации.
uv run aether-dataset publish \
  --output /data/loquacious-medium-mimi \
  --repo manifestro/stage1_aether
```

`publish` требует `HF_TOKEN`, создаёт или использует только приватный dataset repo,
публикует каждый шард вместе с checksum receipt и безопасно пропускает уже
подтверждённые remote shards при повторном запуске. Токен не сохраняется в кеше,
конфигурации, логах или notebook.

Перед полным прогоном `benchmark` должен проверить несколько характерных длин
аудио, подобрать batch budget для доступной GPU и сохранить выбранные параметры.
Цель — максимальная устойчивая загрузка устройства без OOM и без изменения токенов
по сравнению с одиночным кодированием.

### Интерактивный экран прогресса

Во время `run` терминал обновляется регулярно и показывает как минимум:

```text
Split / текущий shard
Обработано примеров / всего примеров
Обработано часов / всего часов
Общий прогресс, %
Текущая и средняя скорость, audio-hours/hour и realtime factor
Прошедшее время и ETA
Успешные записи и ошибки
Текущий batch size и суммарная длительность batch
GPU utilization, VRAM used/total, temperature и power draw (если доступны)
CPU utilization и RAM used/total
Свободное место на output filesystem
Заполнение decode, GPU и writer queues
```

Основной процент рассчитывается по суммарной длительности аудио, а не по количеству
файлов: короткие и длинные записи имеют разную стоимость. ETA рассчитывается по
скользящему окну фактической производительности и помечается как предварительный,
пока не накоплено достаточно наблюдений.

GPU-метрики читаются через NVML, когда он доступен. Отсутствие NVML не должно
останавливать обработку: соответствующие показатели отображаются как недоступные.

### Логи и работа без терминала

Помимо интерактивного экрана, прогон пишет машиночитаемый `run_metrics.jsonl`.
Каждая запись содержит timestamp, общий прогресс, throughput, ETA, номер шарда,
счётчики ошибок и доступные показатели GPU/CPU/RAM/disk. Поэтому состояние можно
восстановить после закрытия терминала или анализировать на удалённой машине.

CLI должен корректно обрабатывать `SIGINT` и `SIGTERM`: прекратить приём новых
batch, завершить или безопасно отменить текущую запись, закрыть writer и оставить
последний подтверждённый шард пригодным для `--resume`. Временный незавершённый
шард никогда не отмечается как `complete`.

Для долгого запуска вывод не должен зависеть от интерактивного TTY. При перенаправлении
в файл CLI автоматически использует обычные периодические строки логов вместо
перерисовки экрана.

## Критерий готовности

Кеш считается готовым только после того, как:

1. обработаны `medium/train`, официальный `dev` и официальный `test` из
   зафиксированной ревизии LoquaciousSet;
2. все Parquet-шарды читаются и соответствуют схеме;
3. пройдены инварианты для каждой успешной записи;
4. подтверждена эквивалентность одиночного и пакетного кодирования;
5. заполнен `dataset_info.json` без placeholder-значений;
6. каждый опубликованный шард имеет подтверждённую запись в `shards.jsonl`;
7. опубликованы итоговые статистика и список ошибок;
8. `status`, `validate` и безопасный `--resume` проверены на тестовом прогоне.
